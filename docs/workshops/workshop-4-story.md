# Presenter story · The Day the Agent Broke the Bank

Open `/workshop-4?view=presenter`. Flo Bank is a fictional bank. NegotiatorBot negotiates disputes; PaymentsAgent executes settlements. Attendees are the response team investigating an apparently valid payment. The protected platform still serves legitimate work.

**Opening:** “The credentials were valid. The request passed schema validation. The bank still lost ₹90 lakh. What did we authorize?” Show 900,000,000 paise, API 200, valid credentials. Withhold the ticket until chapter two. Collect local predictions; no polling service is needed.

| Minutes | Story and demonstration | Audience task / evidence |
|---|---|---|
| 0–8 | The bank has already paid. Show loss and valid request. | Vote identity/model/tool policy/approval. |
| 8–20 | Follow the money. Reveal ticket, recorded proposal and NegotiatorBot → PaymentsAgent. Execute separate vulnerable ledger replay. | Mark where untrusted information became authority; compare both ledgers. |
| 20–33 | Contain the reasoning loop. Gate 1 budget denial; optional bounded live review. | Predict whether inference refusal/denial stops a direct tool call. Test distinction. |
| 33–53 | Control the capability. Gate 2 identity and actual arguments. Isolate beneficiary and ceiling denials. | Repair local prepared policy; inspect a denial and one permitted payment. |
| 53–60 | Attacker changes routes. Attempt direct API bypass. | Inspect audience/scopes; select missing constraint. |
| 60–67 | Break and checkpoint recovery. Display “Can the payment agent approve itself?” | Rest; facilitator restores stalled labs. |
| 67–85 | Restrict identity. Audience separation, token exchange and scope limits. | Compare prepared identity configurations; wrong audience and scope escalation. |
| 85–103 | Approval attaches to a transaction. Reject self approval, approve independently, reject tampering, inspect retry. | Review exact proposal immediately before review; prove one settlement. |
| 103–119 | Second agent, second boundary. Legitimate delegation, foreign access, completion and binding. | Identify principals permitted to read/execute/approve/complete; inspect actual results. |
| 119–130 | Prove repair. Run attack suite and legitimate business path; reconstruct familiar evidence. | Explain one denial and one successful bound payment. |
| 130–135 | Incident review. Revisit original votes. | Complete control-owner and production-readiness worksheet. |

At every chapter use **predict → run → inspect → change → retest**. Use at most seven minutes of uninterrupted explanation. Give each pair one task and one artifact. Timebox stalled exercises and supply completed checkpoints. Show traces as early evidence; the final reconstruction assembles familiar records. The console’s chapter progression is a presenter aid, while technical service results determine success.

The ₹90 lakh proposal is recorded, and the isolated vulnerable ledger executes it. Do not describe it as a live model compromise. The optional live comparison is one bounded inference call; a refusal or provider failure is visible evidence, never a reason to relabel replay as live. Console requests select fixed scenarios and server-owned identifiers. Its view switches and predictions have no enforcement role.

The final successful business path is delegate → propose → independently approve → execute exact arguments → bind actual payment to task. End with a correctly bound payment alongside blocked attacks, then discuss production ownership for identity, distributed budgets, availability and durable audit operations.
